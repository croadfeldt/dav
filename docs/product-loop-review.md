# Product-loop review — the five stages, the missing spine, and the UX contract

**Contract: this document settles three things.** (1) Where the console stands
against the product's goal chain, stage by stage — what data each stage uses,
creates, and who consumes it. (2) The design of the **gap ledger**, the missing
spine that connects the stages. (3) The UX contract every surface must meet:
smooth, usable, **no tribal knowledge required, simpler is better** (Chris,
2026-07-31). Sections 5–6 are the sequenced change list. Findings here come
from a live walkthrough (2026-07-30/31): the fixtures project rendering 41
results against zero use cases, and an engineering roadmap whose every item is
dead text.

The goal chain, verbatim (Chris, 2026-07-31):

> Find the gaps, identify solutions, derive solutions, modify source to include
> the solutions, revalidate. Along the way: identify core capabilities,
> identify most important / used items, build roadmaps for engineering and
> consumers, group capabilities.

**One-sentence conclusion:** stages 1 and 5 have machinery and stage 1 is
calibrated; stages 2–3 exist disconnected; stage 4 is missing; the gap ledger
is the spine that connects all five and turns both roadmaps from reports into
live views.

## 2. The gap ledger (the missing spine)

One row per (project, canonical gap). The ledger is the ONLY place lifecycle
state lives; analyses remain immutable evidence.

```
gap_ledger
  id, project_id
  capability_id        -- catalog identity (existing canonicalization)
  title, severity      -- denormalized from latest supporting analysis
  state                -- open | acknowledged | addressed | verified_closed | regressed | retired
  first_seen_run       -- run_id + analysis pointer (evidence)
  last_seen_run        -- most recent run that reproduced it
  demanding_ucs        -- uuid[] (drives demand weighting)
  proposal_ref         -- enhancement proposal id (stage 2-3 link)
  change_ref           -- PR/MR URL (stage 4 link)
  verify_run           -- run_id that showed it absent on the change's branch (stage 5 evidence)
  guidance             -- operator steering text captured at dispatch (durable)
  updated_by, updated_at
```

Lifecycle and who writes each transition:

- `open` — ingest creates/refreshes the row when a quorum gap lands (existing
  canonicalization path; no new analysis work).
- `acknowledged` — human, one click, optional note.
- `addressed` — set when a proposal or PR is attached (stage 3/4).
- `verified_closed` — **only** a revalidation run may set this: the gap's
  demanding UCs re-ran against the change ref's branch and the gap did not
  reproduce. Recorded with the run id. Never set by hand.
- `regressed` — ingest sets it automatically when a `verified_closed` gap
  reproduces later. This is the honesty mechanism; it replaces silent
  disappearance/reappearance.
- `retired` — human: won't-fix / not-a-gap, with reason (feeds the analyzer's
  false-positive review).

The delta report falls out for free: after each run, ingest emits
`{new: [...], still_open: [...], closed_candidates: [...], regressed: [...]}`
against the ledger — the "what changed since last run" artifact that today
requires eyeballing two runs.

## 3. The two roadmaps — ledger views, not reports

- **Engineering roadmap** = the ledger queued for builders. Order =
  severity × UC demand × foundational weight (all three already computed).
  Every item navigates (§4 rule 4) and shows its lifecycle state. The
  markdown export stays — it is the meeting artifact.
- **Consumer roadmap** = the same ledger inverted for adopters, per persona:
  *adopt now* (capabilities with no open gaps for your persona's criteria),
  *coming* (gaps addressed/awaiting verification, with change refs),
  *do not build against yet* (open critical/major, with why-not citations).
  This is the enablement artifact the UX ruling identified as the keystone
  gap; it requires zero new analysis — only the ledger and persona verdicts
  that already exist.

## 4. The UX contract

Standing acceptance criteria for every surface, existing and new. A surface
that fails one of these is a defect, not a style preference.

1. **The front door answers the product question.** Landing view = the
   readiness board: UC × persona verdict matrix, latest-eval-per-UC, drill-in
   to cited why-not. Runs, turns, and pipelines are the engine room — one
   level down, reached from the evidence they support, never the landing page.
2. **No tribal knowledge.** Every number, chip, and empty state explains
   itself in place: "0/0 evaluated" must say *why* (e.g. "this project has no
   use cases — import or author them; analyses exist but have nothing to
   attach to") and link to the fix. If understanding a view requires having
   read a design doc or this repo's history, the view is wrong.
3. **Simpler is better: one decision artifact per question.** Readiness board
   ("where do we stand"), gap ledger + delta ("what changed, what's being
   done"), two roadmaps ("what next, for builders / for adopters"). Surfaces
   that don't serve one of those either merge into one that does or are
   labeled **experimental** and moved out of the primary nav (today:
   assessment ingest, capability dispositions/strategic-fit).
4. **No dead ends.** Anything rendered as an item navigates to its evidence
   or its action. A styled card with no handler (the entire current roadmap)
   is a defect class, and the review that found it should not be needed
   twice: a UI check — every `data-*`-less card in a list view fails CI — is
   cheaper than rediscovering this by user report.
5. **Trust is provenance, shown where the claim is.** Every verdict/readiness
   surface carries the instrument badge: "measured by <model> · battery
   P 0.947 / R 0.900 · <date>" linking to the calibration table. Calibration
   living only in a settings tab hides the product's strongest property.
6. **One source of UC truth per project.** The two-spine split (corpus files
   vs managed UCs) caused "41 results, 0 use cases." Rule: ingest
   auto-materializes managed UC rows for any analyzed UC not already present
   (marked `source: corpus`), so every UC-joined view always has its spine.
   Imports refine; they are never a precondition for seeing your own results.

## 5. Sequenced change list

Ordered so each step is independently shippable and nothing waits on the UI
reshuffle:

1. **Ledger substrate** — migration + ingest transitions (`open`,
   `regressed`, closure candidates) + delta computation. No UI yet.
2. **Auto-materialize corpus UCs at ingest** (§4.6) — kills the two-spine
   defect class.
3. **Roadmap navigation + state** — wire gap→UC-evidence and
   cluster→capability drill-ins; show ledger state per item. (The cheap fix
   that makes today's roadmap usable while the rest lands.)
4. **Delta report view** — per-run "what changed" panel + the readiness-board
   landing page (§4.1), calibration badge (§4.5).
5. **Gap→proposal linkage** — "propose fix" on a ledger row seeds the
   enhancement workbench with the gap's cited why-not; proposal id lands in
   `proposal_ref`.
6. **Stage 4: guided agent runner** — work-order export (ledger row +
   guidance box), PR-only headless runner, `change_ref` attach; revalidation
   run on the branch sets `verified_closed`. Pilot manually first (one gap,
   operator-guided) before any orchestration.
7. **Consumer roadmap** — the per-persona enablement view over the ledger.

## 6. Explicitly out of scope / deferred

- n=2 quorum experiments, model routing changes — orthogonal, battery-gated
  separately.
- Automated merge of agent PRs — never; human merge is a permanent guardrail.
- Assessment-ingest / disposition surfaces — remain experimental until they
  feed one of the three artifacts, per §4.3.
